# 分析模式细节：ladder 与 geo

从 SKILL.md 拆出。**在用到这两个模式时读。**
`scan` 模式的判读规则见 SKILL.md；引擎细节见 engine-global.md / engine-cn.md。

## 收窄阶梯：把宽词拆成窄口（--mode ladder）

```bash
python3 scan.py --mode ladder "invoice" --limit 8
```

把一个宽词拆成更窄的变体，逐个测供给并按饱和度排序。候选来自修饰语模板
（`for teachers` / `template` / `export`）和**真实自动补全词**——后者更值钱，
因为它们是确实存在的窄口。

两条必须知道的规则：

1. **0 仓库不代表「处女地」，代表「这个词没人用」。** 脚本已过滤 <3 仓库的变体。
   真正的窄口是有一定供给（说明需求被承认）但显著少于原词。
2. **品牌词不是市场。** 补全列表里的单词条目几乎总是品牌（`invoicenow`），
   其衍生词会被一并排除——那是某家公司的产品线，不是你能进的战场。

成本：每个变体一个 GitHub 搜索请求，受**未授权 10 次/分钟**约束，
脚本会主动读配额并等待重置（命中缓存则秒回）。所以 `--limit 12` 实测要几分钟，
不是 12 秒——用 `--limit` 控制规模。设 `GITHUB_TOKEN` 可提到 30 次/分钟。

**窄 ≠ 好。** 阶梯只说明「战场小」，不说明「有人付钱」。

## 地理套利：找竞争真空的国家（--mode geo）

```bash
python3 scan.py --mode geo "receipt scanner" --regions us,cn,br
```

同一需求在不同国家的竞争结构可以差几百倍。实测 `receipt scanner`：
美国头部 7,642,608 条评价，中国头部 **18,311** 条。

**关键：工具按各地区自身的 App 生态基准做归一化。** 绝对数字会同时误导
两个方向——把小市场里的正常品类看成机会，也把大市场里的真缺口看成没市场。
`todo list app` 在巴西按原始数字是 29x 套利，但巴西头部已有 34,919 条评价
（已被服务的市场）；归一化后差距是 14x。原始数据与实测值见
`references/calibration.md`。

**然后必须问「这个差距为什么存在」。** 壁垒正是它没被占的原因，
也是你的进入成本：语言、支付、税务、本地渠道。

**看到「⚠️ 口径限制」不要忽略。** 某个地区的生态基准 App 取数失败时，
归一化分母会退化成 1，该地区的饱和度被放大几个数量级——「成熟/空白市场」
的选择会被整个翻转。工具会明确列出受影响的地区并要求重跑
（基准 App 有 7 天缓存，重跑通常即可命中）。
