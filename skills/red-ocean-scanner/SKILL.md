# 避红海扫描 · Red Ocean Scanner

## 一句话原则

**存量少不等于机会，存量少可能只是没人关心。** 判断必须同时看需求和供给，
而且**需求侧的"愿不愿意掏钱"比供给侧的"有没有人做"更重要**。

这个 skill 的存在就是为了防止一个具体错误：**只看供给就下结论。**
下面所有规则都是从真实反例里总结的，不是理论。

## 选择市场引擎

两个市场的**可靠信号完全不同**，所以是两个独立引擎，不是一个参数开关。
强行合并会得到一个两个市场都不准的工具。

```bash
cd <skill目录>

python3 scan.py --engine global "veterinary clinic software"   # 全球/英文
python3 scan.py --engine cn     "代账公司对账单"                  # 中文
python3 scan.py --engine both   "invoice excel"                 # 同词双市场对比
python3 scan.py --list-engines
```

### 三种分析模式（避红海的核心工作流）

| 模式 | 回答什么问题 | 用法 |
|---|---|---|
| `scan` | **这个词**是不是红海？ | `--mode scan`（默认） |
| `ladder` | 换成哪个**更窄的词**就不是？ | `--mode ladder "invoice" --limit 8` |
| `geo` | 换到哪个**国家**就不是？ | `--mode geo "receipt scanner" --regions us,cn` |

**最重要的一条规则：红海是「词」的属性，不是「需求」的属性。**
`invoice app` 有 17,249 个仓库（红海），`invoice export` 只有 1,826 个。
需求相同，战场小十倍。别问方向是不是红海，问**这个词**是不是红海。

参数约定：调度器选项在关键词**前**，目标脚本选项在**后**。

### 两个市场引擎

| 引擎 | 市场 | 可靠信号 |
|---|---|---|
| `global` | 全球/英文 | App Store 评价数 + GitHub 仓库密度 + 三源自动补全 |
| `cn` | 中文 | 微信内容存量 + 360 相关搜索 |

全球引擎自动判断**消费级**还是 **B2B**，也可用 `--market` 手动指定。
设 `GITHUB_TOKEN` 可把 GitHub 冷却从 22s 降到 7s。纯标准库，无需 API key。

## 怎么读裁决

### 裁决来自决策矩阵，不是单一分数

供给和需求**分开测**，因为它们是两个问题。合并成一个分数会把两种完全相反的
死局混为一谈。

| | 需求强 | 需求弱 |
|---|---|---|
| **供给薄** | 🟢 **机会** | 🟠 **无人区**（别做） |
| **供给厚** | 🔴 **红海** | 🔴 **红海** |

**🟠 无人区是最容易上当的一格。** 多数选品建议只说「找竞争少的地方」，
但供给少有两种相反原因：没人做，和没人要。只看供给会把「没人要」当「没人做」。

### 裁决优先级与覆盖度

```
否决项  >  覆盖度不足  >  决策矩阵
```

**否决项一律判红。** 真实教训：`receipt scanner` 的 GitHub 仅 1,400 仓库
（供给薄）、需求也旺，但 App Store 头部是 **764 万条评价的免费产品**。
综合评分会让这个事实被别的分数抵消。

`绿(覆盖度低)` = 只测到 2 个维度（B2B 没有 App Store 判据），是**真实的
信息缺口**，标注出来而不是假装有把握。**分数只用于排序**，只反映供给健康度。

## 另外两个分析模式

| 模式 | 作用 | 一句话要点 |
|---|---|---|
| `--mode ladder` | 把宽词拆成更窄的变体 | **0 仓库不是处女地，是没人用的词**；品牌词不是市场 |
| `--mode geo` | 找竞争真空的国家 | 必须按各地区**自身生态基准归一化**，否则绝对数字双向误导 |

用法与实测输出见 `references/modes.md`。

## 信号可靠性分级

实测得出的分级。**只有可靠信号计入评分**，噪声信号一律降级为参考。

### 可靠 — 计入评分

| 信号 | 引擎 | 实测区分度 |
|---|---|---|
| GitHub 仓库数 | global | **4000 倍量级**：todo app 90,582 vs 兽医排班 117 |
| 头部仓库 star 分布 | global | 14,139★（habit tracker，红海）vs 2★（殡葬管理，缺口） |
| 微信内容存量 | cn | 8580（摸鱼，红海）vs 511（代账对账单，缺口） |
| 标题信号（付费工具/自己做） | cn | 能区分"有人靠它赚钱"与"壁垒已归零" |
| 360 相关搜索词 | cn | 真实搜索行为，高购买意图词可数 |

### 噪声 — 仅作参考，不计分

| 信号 | 为什么不可靠 |
|---|---|
| **StackOverflow 搜索** | 模糊匹配，噪声极大。实测 `invoice excel` 匹配到 Automapper 问题；`funeral home management` 匹配到 UIPickerView 问题。**已停用** |
| **npm / PyPI 搜索** | 同样是模糊匹配。`sports team scheduling` 返回 52,825 个包，无意义 |
| GitHub issues | 混合 bug 报告与功能请求，需人工读标题判断 |

### 原则：宁可漏判，不可误判

**一个会给出错误绿灯的工具，比没有工具更糟。** 所以只把可验证的信号计入
评分，宁可少给绿灯，也不把噪声当证据。

## 数据源能力（结论速查）

完整矩阵、静默失败陷阱与已删除信号见 `references/data-sources.md`。

- **✅ 已接入**：Google/Bing/DDG 自动补全（需求）· iTunes App Store（消费级供给）·
  GitHub（开发者供给）· 360 搜索 + 搜狗微信（中文市场）
- **❌ 平台封锁 403**（不是网络问题，别浪费时间绕过）：Reddit · Product Hunt ·
  G2 · Capterra · AlternativeTo
- **⚠️ 已停用**（噪声大于信息）：StackOverflow 模糊搜索（改用精确的 `inname` 标签）·
  npm/PyPI 搜索（只用精确下载量端点）· SERP 评测站密度（各源都限流）
- **⚪ 不适用**：实体产品与线下服务（手工皂、蜡烛、餐饮…）。竞争格局不在
  GitHub 也不在 App Store 上，工具会拒绝作答而不是硬给自信的错误裁决。
  想评估**给这个行业做软件**，把查询改成工具本身。

**两条维护者须知**：① 连通性结论必须用**目标运行时**复验（早期误判 Google
不可达，只因用 Node 的 `fetch` 测）。② App Store 评价数**对 B2B 无效**，
引擎会标注「口径限制」而非硬给分数。

## 盲点扫描（每次分析都要过一遍）

这三组决定「同样的努力能换多少钱」，且不出现在任何平台清单里。
**候选池空了就从这里找，而不是继续换关键词。**

### 七条结构性规律

1. **「有人做但做得烂」永远比「没人做」值钱。** 没人做常常是因为不赚钱。
2. **钱在重复收费里。** 订阅 > 买断 > 广告分成；内容平台分成是最差的一档。
3. **买家选「正在赚钱的人」**（卖家、代账公司、诊所），不是「想赚钱的人」
   （同行、小白）。前者算得清 ROI，后者是焦虑税。
4. **分发先于产品。** 先答"用户怎么找到我"，再做产品。
5. **不用登录/版号/备案的形态优先**，把合规成本压到零。
6. **AI 含量越高的环节越不值钱**；判断、信任、合规在升值。
7. **开源会压制付费意愿**——但换成企业买家可能仍然成立。

### 工具**看不见**的五件事

比上面七条更重要：防止用户误以为工具给了全局视野。

1. **蓝海在定义上搜不到。** 还没被命名的需求，补全里没有、GitHub 上没有。
   工具系统性偏向「已被讨论过的需求」，不适合回答「有没有全新的需求」。
2. **只看英文和中文。** 其他语言市场几乎不可见——这既是局限，也是方向。
3. **看不到你的准入成本。** 竞争稀薄不等于你进得去（资质、渠道、人脉）。
4. **看不到时机。** 无法区分「还没人做」和「做过但失败了」。
5. **平台规则变化会重置结论**——数据只是某时点的快照。

### 六类结构性缺口（引导用）

1. **监管刚变的地方**——新规同时创造「必须做」和「没人会做」。
2. **大厂刚关停的服务**——用户还在，工具没了；搜「XX 替代」是最快入口。
3. **平台刚开的新品类**——平台花钱买供给的时期，是个人最高时薪。
4. **被语言挡住的成熟市场**——用 `--mode geo` 找，壁垒就是护城河。
5. **「必须人工判断」的环节**——AI 打平生产，打不平责任与信任。
6. **某个行业的脏活**——越小、越不性感，越可能没竞争。

## 标准工作流

1. 判断市场（中文区还是英文区），选对应引擎
2. 列 6–10 个候选关键词（从自己和身边人的抱怨里找）
3. 跑扫描，拿红黄绿排名
4. **只对绿灯项**做付费验证（见引擎参考文件）
5. 按盲点扫描复核
6. 只留一个，花一周做落地页，**不写产品代码**
7. 判断标准：有没有陌生人在 6–8 周内主动掏钱

## 最后：边界与分工

| | 谁负责 | 怎么用 |
|---|---|---|
| **避开红海** | 工具（可验证） | `scan` 排掉红海与无人区；`ladder` 换更窄的词；`geo` 换竞争真空的国家 |
| **发现蓝海** | 你（框架辅助） | 读 `references/blue-ocean-methods.md` |

**三条必须主动说明的边界**：

1. **不做**：证明有人愿付钱。两个引擎都是**意图/供给数据**，不是成交数据。
2. **看不到**：非英文/中文市场、消费级之外的生态、以及**尚未被命名的需求**
   ——蓝海在定义上就搜不到。
3. **测不出**：护城河。工具只答"有没有人在做"，不答"你做出来守不守住"。

> 工具负责**排除**，你负责**创造**。把工具当灵感来源，只会得到一堆没人要的窄口。
