# 避红海扫描 · Red Ocean Scanner

## 一句话原则

**存量少不等于机会，存量少可能只是没人关心。** 判断必须同时看需求和供给，
而且**需求侧的"愿不愿意掏钱"比供给侧的"有没有人做"更重要**。

这个 skill 的存在就是为了防止一个具体错误：**只看供给就下结论。**
下面所有规则都是从真实反例里总结的，不是理论。

## 一、选择市场引擎

两个市场的**可靠信号完全不同**，所以是两个独立引擎，不是一个参数开关。
强行合并会得到一个两个市场都不准的工具。

```bash
cd <skill目录>

python3 scan.py --engine global "veterinary clinic software"   # 全球/英文
python3 scan.py --engine cn     "代账公司对账单"                  # 中文
python3 scan.py --engine both   "invoice excel"                 # 同词双市场对比
python3 scan.py --list-engines
```

### 三种分析模式（这才是避红海的核心工作流）

| 模式 | 回答什么问题 | 用法 |
|---|---|---|
| `scan` | **这个词**是不是红海？ | `--mode scan`（默认） |
| `ladder` | 换成哪个**更窄的词**就不是？ | `--mode ladder "invoice" --limit 8` |
| `geo` | 换到哪个**国家**就不是？ | `--mode geo "receipt scanner" --regions us,cn` |

**最重要的一条规则：红海是「词」的属性，不是「需求」的属性。**
`invoice app` 有 17,249 个仓库（红海），`invoice export` 只有 1,826 个（窄口）。
需求是同一个，战场小十倍。所以不要问「这个方向是不是红海」，
要问「这个词是不是红海」，然后换词。

参数约定：调度器选项写在关键词**前面**，目标脚本选项写在关键词**后面**。

| 引擎 | 市场 | 可靠信号 | 产出 |
|---|---|---|---|
| `global` | 全球/英文 | App Store 评价数（消费级）+ GitHub 仓库密度（开发者）+ 三源自动补全（需求） | 三类市场视角 |
| `cn` | 中文 | 微信内容存量 + 360 相关搜索 | 搜索意图视角 |

全球引擎会自动判断是**消费级**还是 **B2B** 市场，因为两者的判据不同：
消费级看 App Store 评价数，B2B 看别的（企业买家不写评价）。
可用 `--market consumer|business` 手动指定。

也可以直接调用底层脚本（`global_scan.py` / `red_ocean_scan.py`）。
统一入口会自动用各引擎自己的冷却策略，**推荐始终用 `scan.py`**。

**可选提速**：设置 `GITHUB_TOKEN`（或 `GH_TOKEN`）环境变量后，全球引擎的
GitHub 限流从 10 次/分钟提升到 30 次/分钟，词间冷却自动从 22s 降到 7s，
不需要改任何代码。中文引擎不受影响。

纯 Python 3.8+ 标准库，**无需 pip install，不需要 API key**。

# 第一部分：通用判读

## 二、怎么读裁决

| 裁决 | 分 | 含义 | 动作 |
|---|---|---|---|
| 🟢 绿 | 8–10 | 值得投入一周验证 | 去做付费验证，别急着写代码 |
| 🟡 黄 | 5–7 | 有硬伤 | 换更窄的关键词重扫，或只当引流工具 |
| 🔴 红 | 0–4 | 别做 | 放弃，**不要靠加功能挽救** |
| 🟡 黄(不完整) | — | 数据没取到 | 稍后重跑，**不要在这个结论上做决定** |

**「否决项」比分数重要，而且是硬性的。** 裁决优先级是：

```
数据不完整  >  否决项  >  分数
```

出现任何否决项**一律判红，不看分数**。这条规则来自真实教训：
`receipt scanner` 的 GitHub 只有 1,400 仓库（低供给），分数 5/10 本该是黄灯，
但 App Store 头部是 764 万条评价的免费产品。分数会掩盖致命否决项，
所以否决项必须能一票压过它。

否决项是「这个方向从结构上就不成立」，不是「需要努力克服」。

**分数只反映供给健康度，不反映需求大小。** 需求必须人工验证（见第八节）。

## 三、信号可靠性分级（本 skill 最重要的方法论）

实测得出的分级。**只有可靠信号计入评分**，噪声信号一律降级为参考。

### 可靠 — 计入评分

| 信号 | 引擎 | 实测区分度 |
|---|---|---|
| GitHub 仓库数 | global | **4000 倍量级**：todo app 90,582 vs 兽医排班 117 |
| 头部仓库 star 分布 | global | 14,139★（habit tracker，红海）vs 2★（殡葬管理，缺口） |
| 微信内容存量 | cn | 8580（摸鱼，红海）vs 511（代账对账单，缺口） |
| 标题信号（付费工具/自己做） | cn | 能区分"有人靠它赚钱"与"壁垒已归零" |
| 360 相关搜索词 | cn | 真实搜索行为，高购买意图词可数 |

### 噪声 — 仅作参考，不计分

| 信号 | 为什么不可靠 |
|---|---|
| **StackOverflow 搜索** | 模糊匹配，噪声极大。实测 `invoice excel` 匹配到 Automapper 问题；`funeral home management` 匹配到 UIPickerView 问题。**已停用** |
| **npm / PyPI 搜索** | 同样是模糊匹配。`sports team scheduling` 返回 52,825 个包，无意义 |
| GitHub issues | 混合 bug 报告与功能请求，需人工读标题判断 |

### 设计原则：宁可漏判，不可误判

**一个会给出错误绿灯的工具，比没有工具更糟。** 所以本 skill 只把可验证的
信号计入评分，宁可少给绿灯，也不把噪声当证据。

## 四、数据源能力（**已修正，附方法论教训**）

### 教训：测试工具本身也会错

早期版本声称 Google / Wikipedia / DuckDuckGo 不可达。**那是错的。**
错误来源：用 Node 的 `fetch` 做连通性测试，而本机 Node 的 DNS 解析异常，
所有请求 CONNECT_TIMEOUT。改用 Python `urllib`（本 skill 的实际运行时）重测后
绝大多数源可用。

| 源 | curl | Python urllib | Node fetch |
|---|---|---|---|
| google.com | ✅ 200 | ✅ 200 | ❌ 超时 |
| en.wikipedia.org | ✅ 200 | ✅ 200 | ❌ 超时 |
| html.duckduckgo.com | ✅ 200 | ✅ 200 | ❌ 超时 |
| www.reddit.com | — | ⚠️ 403 | ❌ 超时 |

**结论：连通性结论必须用目标运行时复验，不能用另一个 HTTP 客户端代测。**

### ✅ 可用（已接入）

Google / Bing / DuckDuckGo 自动补全 · iTunes(App Store) API · GitHub API ·
DuckDuckGo HTML 搜索 · 360 搜索 · 搜狗微信

### ❌ 真不可用（平台主动封锁，不是网络问题）

Reddit（含 old.reddit 与 .json）· Product Hunt · G2 · Capterra · AlternativeTo
——全部 HTTP 403，需要官方 API key 或付费数据源。**不要浪费时间绕过。**

### ⚠️ 噪声过大，已停用

| 源 | 为什么停用 |
|---|---|
| StackExchange | 模糊匹配。`invoice excel` 匹配到 Automapper 问题；`funeral home management` 匹配到 UIPickerView 问题 |
| npm / PyPI 搜索 | 同样模糊。`sports team scheduling` 返回 52,825 个包 |
| Google 搜索页 | JS 重渲染，服务端 HTML 里结果标题几乎为空 |

完整矩阵见 `references/data-sources.md`。

### 仍然存在的局限

**B2B 市场只能弱判。** App Store 评价数对 B2B 无效（企业买家不写评价：
B2B 兽医软件头部 4 万条 vs 消费级 764 万条），而 G2/Capterra 被封锁。
引擎检测到 B2B 会主动标注「口径限制」，不硬给分数。

## 四之二、收窄阶梯（ladder_scan.py）

```bash
python3 scan.py --mode ladder "invoice" --limit 8
```

把一个宽词自动拆成更窄的变体，逐个测供给，按饱和度排序。
候选有两个来源：修饰语模板（`for teachers` / `template` / `export`）和
**真实自动补全词**（后者更值钱，因为它们是确实存在的窄口）。

实测输出：

```
原词：145,975 个 GitHub 仓库 [红海]
invoice for nonprofits        3 仓库  极低   48658.3x
invoice for teachers         22 仓库  极低    6635.2x
invoice for landlords        24 仓库  极低    6082.3x
```

两条必须知道的规则：

1. **0 仓库不代表「处女地」，代表「这个词没人用」。** 脚本已过滤 <3 仓库的
   变体。真正的窄口是有一定供给（说明需求被承认）但显著少于原词。
2. **品牌词不是市场。** 补全列表里的单词条目几乎总是品牌
   （`invoicenow`、`receiptify`），它们的衍生词（`invoicenow iras`）会被
   一并排除——那是某家公司的产品线，不是你能进的战场。

成本：每个变体约 12 秒（GitHub 未授权限流）。用 `--limit` 控制规模，
设 `GITHUB_TOKEN` 可提速 3 倍。

**窄 ≠ 好。** 阶梯只说明「战场小」，不说明「有人付钱」。必须回到 `scan` 模式
和付费验证。

## 四之三、地理套利（geo_scan.py）

```bash
python3 scan.py --mode geo "receipt scanner" --regions us,cn,br
```

同一需求在不同国家的竞争结构可以差几百倍。实测：

| 地区 | `invoice` 头部 | `receipt scanner` 头部 |
|---|---|---|
| 美国 | 265,331 评 | 7,642,608 评 |
| 中国 | **193** 评 | 18,311 评 |
| 巴西 | 3,458 评 | 47,821 评 |

**关键：工具会按各地区自身的 App 生态基准做归一化。**
绝对数字会同时误导两个方向——把小市场里的正常品类看成机会，
也把大市场里的真缺口看成没市场。

开发中抓到一个真实假阳性：`todo list app` 在巴西按原始数字看是 29x 套利，
但巴西头部 todo app 有 34,919 条评价——那是个已经被服务的市场。
归一化后差距是 14x，不是 29x。

**然后必须问「这个差距为什么存在」。** 壁垒正是它没被占的原因，
也是你的进入成本：语言、支付、税务、本地渠道。

## 五、盲点扫描（每次分析都要过一遍）

这些不出现在任何平台清单里，但决定同样的努力能换多少钱：

### 七条结构性规律

1. **「有人做但做得烂」永远比「没人做」值钱。** 没人做常常是因为不赚钱。
2. **钱在重复收费里。** 订阅 > 买断 > 广告分成。内容平台分成是最差的一档。
3. **买家要选「正在赚钱的人」**（卖家、代账公司、诊所、从业者），不是
   「想赚钱的人」（同行、小白）。前者算得清 ROI，后者是焦虑税且窗口在关。
4. **分发先于产品。** 先答"用户怎么找到我"，再做产品。
5. **不用登录/版号/备案的形态优先**，把合规成本压到零。
6. **AI 含量越高的环节越不值钱。** 内容生产已被 AI 打平；判断、信任、合规
   这些 AI 做不了的环节在升值。
7. **开源会压制付费意愿。** 如果头部是成熟开源项目，买家是开发者时基本收不到钱；
   但换成企业买家可能仍然成立。这条在全球市场尤其重要。

### 本工具**看不见**的东西（每次都要主动说明）

这一节比上面七条更重要，因为它防止你误以为工具给了你全局视野。

**① 蓝海在定义上搜不到。** 本工具测的是搜索与供给数据。
一个还没被命名的需求，自动补全里不会出现，GitHub 上不会有仓库。
**所以工具系统性地偏向「已经被讨论过的需求」**，会漏掉真正的开创性方向。
用法上：工具适合回答「这个词能不能进」，不适合回答「有没有全新的需求」。

**② 只看英文和中文。** 其他语言市场（德语、日语、葡语、阿拉伯语）对本工具
几乎不可见。这既是局限，也是提示——**未被覆盖的语言市场本身就是方向**。

**③ 看不到供给侧的真实成本。** 一个方向可能竞争稀薄，但因为你没有行业资质、
渠道或人脉，实际进不去。工具只测市场结构，不测你的准入条件。

**④ 看不到时机。** 一个市场可能刚被证伪（用户试过、不买单），
数据上却仍显示「供给稀薄」。工具无法区分「还没人做」和「做过但失败了」。

**⑤ 平台规则变化会瞬间重置结论。** 供给侧数据是某个时点的快照。
一次算法改版、一次封号潮、一次政策落地，可以让红海变蓝海，或反过来。

### 六类值得主动去扫的方向（引导用）

当候选池空了，从这些结构性缺口里找，而不是继续换关键词：

1. **监管刚变的地方。** 新规落地会同时创造「必须做」和「没人会做」的窗口。
2. **大厂刚关停的服务。** 用户还在，工具没了。搜「XX 替代」是最快的入口。
3. **平台刚开的新品类。** 平台花钱买供给的时期，是个人能拿到的最高时薪。
4. **被语言挡住的成熟市场。** 用 `geo_scan.py` 直接找，壁垒就是护城河。
5. **「必须人工判断」的环节。** AI 打平了生产，但打不平责任与信任。
6. **某个行业的脏活。** 越小、越不性感、越没人愿意做，越可能没有竞争。

## 六、标准工作流

1. 判断市场：目标用户在中文区还是英文区？选对应引擎
2. 列 6–10 个候选关键词（从自己的抱怨、身边人的抱怨里找）
3. 跑扫描，拿到红黄绿排名
4. **只对绿灯项**做付费验证（见第八节）
5. 按盲点清单复核
6. 只留一个，花一周做落地页，**不写产品代码**
7. 判断标准：有没有陌生人在 6–8 周内主动掏钱

# 第二部分：全球市场引擎（global）

## 七-G、全球引擎怎么工作

```bash
python3 scan.py --engine global "keyword"
```

**供给（计入评分）**
- GitHub 仓库数：<300 极低 / <1500 低 / <5000 中 / <20000 密集 / ≥20000 红海
- 头部仓库 star：≥2000★ = 已有成熟开源替代品（否决项）；<50★ 且仓库少
  = 没有赢家，缺口典型形态

**参考（不计分）**
- GitHub issues 数量与未关闭数——混合 bug 与功能请求，需人工读

## 八-G、全球引擎的校准锚点

实测值，可直接对照：

| 方向 | 仓库数 | 头部★ | 分 | 裁决 |
|---|---|---|---|---|
| funeral home management | 23 | 2 | 9 | 🟢 |
| veterinary clinic scheduling | 117 | 13 | 9 | 🟢 |
| invoice excel | 2,262 | 411 | 5 | 🟡 |
| habit tracker | 60,479 | 14,139 | 2 | 🔴 |
| todo list app | 90,582 | 2,121 | 2 | 🔴 |

**为什么 `invoice excel` 只有 5 分**：2,262 个仓库不算少，且有 411★ 玩家。
它是"能做但要明确差异化"，不是"蓝海"。

## 九-G、全球引擎的付费验证（人工，必做）

GitHub 供给稀薄**只证明没人做，不证明有人买**。全球市场的验证路径：

```
1. 找该行业的垂直社区（不是 Reddit 主版，是行业论坛/Facebook 群/LinkedIn 群）
2. 读真实抱怨，找"现在怎么解决"的描述
3. 看有没有人在卖同类方案：Google "<关键词> software pricing"
   （注意：本 skill 无法自动搜 Google，必须人工）
4. 挂落地页收邮箱，看转化
```

**关键区别**：中文市场看闲鱼成交（能看到真实成交记录），
全球市场看定价页和评测站——两者的"事实"来源不同。

# 第三部分：中文市场引擎（cn）

## 七-C、中文引擎怎么工作

```bash
python3 scan.py --engine cn "关键词"
```

**需求** = 360搜索「相关搜索」词（真实搜索行为，高购买意图词可数）
**供给** = 搜狗微信文章存量 + 标题信号

## 八-C、三类一票否决（每条都有真实反例）

### ① 免费白嫖词 → 用户不是要工具，是要免费

相关搜索出现《永久免费版》《在线免费》《破解》。

**真实反例：`录音转文字`**
供给侧看是完美方向：微信仅 1000 篇（低供给），标题里 **4 条「已有付费工具」
信号**。只看供给会判满分。
但相关搜索是《录音转文字永久免费版》《豆包录音转文字在线免费使用》。
**这是价格战，不是需求。** 评分 10 → 3。

规则：≥4 条免费词封顶 3 分，≥2 条封顶 6 分。

### ② 垄断品牌词 → 该搜索词已被占死

相关搜索出现具体产品名（豆包、讯飞、剪映、鲁青、金蝶…）。
用户在找**那个产品**，不是找解决方案。

**真实反例：`试卷排版`** 9 条高意图词里 3 条是《鲁青答题卡制作工具》。

规则：出现即封顶 4 分。

### ③ 壁垒归零 → 你做完守不住

微信标题出现 `vibecoding`、`我自己做了`、`源码`、`一行代码`。

**真实反例：`房贷提前还款计算器`**
相关搜索里 **6 条高购买意图词，需求看起来很旺**。但标题里躺着
《一天时间 vibecoding 实现房贷提前还款计算器》。
**需求旺 + 壁垒零 = 你进去就是给别人做嫁衣。**

最危险的陷阱：所有需求指标都亮绿灯，只有这一个信号在报警。
规则：出现即封顶 3 分。

### 中文特有的分类陷阱

**B2B 的价格词是正信号，别误伤。**《收费价目表》《报价明细表》《费用》《成本》
在 B2B 语境下是**强购买意图**（用户在评估预算），不是白嫖。

## 九-C、中文引擎的限流防护（重要）

**搜狗微信连续请求会静默返回空页面，而不是报错。** 如果不处理，工具会把
"没抓到数据"误读成"存量 0 篇"，得出**完全相反**的结论。

脚本已内建：
- 空响应退避重试（25s / 50s），**不当作 0**
- 始终取不到时输出 `🟡 黄(不完整)` 并加否决项，**绝不给绿灯**
- 实测限流约 45 秒解除

**看到「黄(不完整)」就隔几分钟重跑，不要将就。**

## 十一-C、中文引擎的付费验证（人工，10 分钟）

扫描能证明「需求旺 + 供给少」，但**证明不了有人真的掏过钱**。

去**闲鱼**搜该关键词，记录：

```
关键词：
有没有人在卖同类产品/服务：有 / 无
价格：
成交/想要数：
评价原文：
```

判读：
- **有人卖且有成交** → 直接开做
- **有人卖但无成交** → 需求可能是伪的，或定价错了
- **没人卖** → 换更窄的关键词重扫

为什么是闲鱼：它是唯一能看到**真实成交**的地方。搜索量是意图，成交是事实。

---

## 最后：这个 skill 的边界

**它做的是**：把"这个方向竞争激烈吗、有没有人在守"从感觉变成可复现的实测。

**它不做**：证明有人愿意付钱。两个引擎都是**意图/供给数据**，不是成交数据。
最终决定永远来自第八节的付费验证。

**它看不到**：消费级市场、非开发者生态。遇到这类方向要主动说明局限，
不要在数据不足时给出绿灯。
