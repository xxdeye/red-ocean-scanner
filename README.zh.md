# 避红海扫描器 · Red Ocean Scanner

[English](README.md) · **中文**

**一个 agent skill：在你花一个月做产品之前，先告诉你这个方向该不该做。**

市面上"找蓝海"的建议大多是感觉。这个是扫描器：实测真实的供给与需求信号，
输出**红/黄/绿裁决**，附证据与否决项。

**同时支持全球市场与中文市场**——用两个独立引擎，因为两个市场的可靠信号
完全不同，合并会得到一个两边都不准的工具。

---

## 它解决什么问题

**「竞争少不等于机会，也可能只是没人关心。」**
这个仓库里的每条规则都来自真实反例，不是理论。

它存在的目的，是防止一个具体错误：**只看供给就下结论。**

### 起因是一个反例

`录音转文字` 在供给指标上看是完美方向：

- 微信只有 **1,000** 篇相关文章——竞争稀薄
- 有 **4** 条标题在推付费/可下载工具——需求已被变现

任何只看供给的分析都会说"做这个"。但需求侧说反话：

```
录音转文字永久免费版
豆包录音转文字在线免费使用
录音转文字在线免费网页版
```

用户不是要找工具，**是在找免费替代品**。这是一个已经打到价格归零、
且有大厂免费产品在场的市场。评分 10 → 3。

---

## 核心方法论：供给 × 需求矩阵

**供给和需求分开测**，因为它们回答两个不同的问题。合并成一个分数，
会把两种完全相反的死局混成同一个中间值：

| | 需求强 | 需求弱 |
|---|---|---|
| **供给薄** | 🟢 **机会** | 🟠 **无人区**（别做） |
| **供给厚** | 🔴 **红海** | 🔴 **红海** |

**🟠 无人区是最容易上当的一格。** 大多数选品建议只教你"找竞争少的地方"，
但供给少有两种完全相反的原因：**没人做**，和**没人要**。
只看供给，你会把「没人要」当成「没人做」。

### 裁决优先级

```
否决项  >  覆盖度不足  >  决策矩阵
```

**出现任何否决项一律判红，不看别的。** 这条来自真实教训：
`receipt scanner` 的 GitHub 只有 1,400 个仓库（供给薄）、需求也旺，
但 App Store 头部是一个**有 764 万条评价的免费产品**。
任何综合评分都会让这个致命事实被别的分数抵消。

`绿(覆盖度低)` 表示只测到 2 个维度（B2B 方向没有 App Store 判据）。
这是**真实的信息缺口**，标注出来而不是假装有把握。

## 安装

纯 Python 3.8+ 标准库。**无依赖，不需要 API key。**

```bash
git clone https://github.com/xxdeye/red-ocean-scanner.git

# 方式 A —— 直接运行
python3 red-ocean-scanner/skills/red-ocean-scanner/scan.py -e global "your keyword"

# 方式 B —— 装成 agent skill
cp -r red-ocean-scanner/skills/red-ocean-scanner ~/.claude/skills/   # Claude Code
cp -r red-ocean-scanner/skills/red-ocean-scanner ~/.dsh/skills/      # DeepSeek Harness
```

## 用法

```bash
cd skills/red-ocean-scanner

# 全球市场
python3 scan.py --engine global "veterinary clinic software"

# 中文市场
python3 scan.py --engine cn "代账公司对账单"

# 同词双市场对比
python3 scan.py --engine both "invoice excel"

# JSON 输出
python3 scan.py --engine global --json "habit tracker"
```

**可选提速**：设 `GITHUB_TOKEN` 后 GitHub 限流从 10 次/分提到 30 次/分，
词间冷却自动从 22s 降到 7s，无需改代码。中文引擎不受影响。

## 三种分析模式（避红海的核心工作流）

| 模式 | 回答什么问题 | 用法 |
|---|---|---|
| `scan` | **这个词**是不是红海？ | `--mode scan`（默认） |
| `ladder` | 换成哪个**更窄的词**就不是？ | `--mode ladder "invoice" --limit 8` |
| `geo` | 换到哪个**国家**就不是？ | `--mode geo "receipt scanner" --regions us,cn` |

### 最重要的一条规则

**红海是「词」的属性，不是「需求」的属性。**

`invoice app` 有 17,249 个 GitHub 仓库（红海），`invoice export` 只有 1,826 个。
需求相同，战场小十倍。所以别问「这个方向是不是红海」，
要问「**这个词**是不是红海」，然后换词。

实测 `ladder` 输出：

```
原词：145,975 个 GitHub 仓库 [红海]
invoice for nonprofits        3 仓库  极低   48658.3x
invoice for teachers         22 仓库  极低    6635.2x
invoice for landlords        24 仓库  极低    6082.3x
```

两条必知规则：

1. **0 仓库不代表「处女地」，代表「这个词没人用」。** 脚本已过滤 <3 仓库的变体。
2. **品牌词不是市场。** 补全列表里的单词条目几乎总是品牌（`invoicenow`），
   其衍生词会被排除——那是某家公司的产品线，不是你能进的战场。

### 地理套利

同一需求在不同国家的竞争结构可以差几百倍。实测：

| 地区 | `invoice` 头部 | `receipt scanner` 头部 |
|---|---|---|
| 美国 | 265,331 评 | 7,642,608 评 |
| 中国 | **193** 评 | 18,311 评 |
| 巴西 | 3,458 评 | 47,821 评 |

**关键：工具按各地区自身的 App 生态基准做归一化。** 绝对数字会同时误导
两个方向——把小市场里的正常品类看成机会，也把大市场里的真缺口看成没市场。

开发中抓到一个真实假阳性：`todo list app` 在巴西按原始数字是 29x 套利，
但巴西头部 todo app 已有 34,919 条评价（已被服务的市场）；归一化后是 14x。

**然后必须问「这个差距为什么存在」。** 壁垒正是它没被占的原因，
也是你的进入成本：语言、支付、税务、本地渠道。

## 评分怎么算

裁决来自**供给 × 需求矩阵**，不是单一混合分数。
**只有可靠信号计入评分**，实测信号质量：

| 信号 | 引擎 | 实测区分度 |
|---|---|---|
| GitHub 仓库数 | 全球 | **4000 倍量级**：todo app 90,582 → 兽医排班 117 |
| 头部仓库 star | 全球 | 14,139★（红海）→ 2★（缺口） |
| App Store 头部评价数 | 全球 | 7,642,608（红海）→ 3,520（缺口） |
| 微信内容存量 | 中文 | 8,675（红海）→ 558（缺口） |
| 360 相关搜索 + 补全词 | 中文 | 真实搜索行为，高购买意图词可数（问法先剔除） |

### 被证伪并删除的信号

| 信号 | 为什么不可用 |
|---|---|
| **StackOverflow 模糊搜索** | 噪声极大。`invoice excel` 匹配到 Automapper 问题；`funeral home management` 匹配到 UIPickerView 问题 |
| **npm / PyPI 搜索** | 同样模糊。`sports team scheduling` 返回 52,825 个包 |
| **App Store「在售产品数」** | 零区分度：所有品类都返回 22-25 款（模糊匹配产物），且错误惩罚 B2B |
| **App Store 评论 RSS** | 实测返回 0 条 |
| **Google 新闻 RSS** | 恒定 100 条，无区分度 |
| **SERP 评测站密度** | DDG/Startpage/Mojeek/searx 全部限流，不稳定 |

**设计原则：宁可漏判，不可误判。** 一个会给出错误绿灯的工具，
比没有工具更糟。所以噪声信号一律降级为「仅供参照」，绝不参与评分。

## 比「避开红海」更进一步：怎么真正找到蓝海

扫描器只能**排除**——它测的是供给与搜索意图，而这两者对**尚未被命名的需求**
都不存在。真正的蓝海通常是创造出来的，永远不会出现在这些数据里。

`references/blue-ocean-methods.md` 讲的正是工具做不到的那部分：

- **护城河（7 Powers）。** 绿灯只证明供给稀薄，不说明你守得住。
  Helmer 的判据是 **Benefit + Barrier**——成本或质量优势，**加上**一个
  对手无法在不伤害自己的前提下复制的东西。大多数看起来不错的生意，
  其实一个 Power 都没有。对单人开发者，实际可得的只有两种：
  **反定位**（在位者不敢跟进的模式）和**转换成本**。
- **ERRC 网格。** `ladder` 只在一个方向上收窄；ERRC 同时动四个维度——
  消除、减少、提升、创造——把价值曲线重画一遍，让竞争变得无关。
  **Create 那一行才是蓝海的来源。**
- **六路径。** 系统性地越过行业边界：替代行业、战略集团、买方群体、
  互补品、功能与情感、时间。

这份文件也明说了扫描器**看不见**什么：未被命名的需求、非英文/中文市场、
你自己的准入成本、时机、以及监管重置。**工具负责排除，你负责创造。**
把扫描器当灵感来源用，只会得到一堆没人要的窄口。

## 边界（重要）

- **只看英文和中文。** 其他语言市场对本工具几乎不可见。这既是局限，
  也是提示——未被覆盖的语言市场本身就是方向。
- **看不到消费级之外。** 两个引擎都是开发者/搜索生态视角，对纯线下生意判断力弱。
- **B2B 只能弱判。** App Store 评价数对 B2B 无效（企业买家不写评价：
  B2B 兽医软件头部 4 万条 vs 消费级 764 万条），而 G2 / Capterra 全部 403。
  引擎会标注「口径限制」而不是硬给分数。
- **这是意图数据，不是成交数据。** 扫描证明「供给薄」，
  **不证明有人掏过钱**。最后一步必须人工：
  - 中文市场 → 去**闲鱼**搜该词，看真实成交记录
  - 全球市场 → 看定价页与评测站，有付费客户才算数
- **搜索引擎类数据源不可靠。** DuckDuckGo 第 3 次请求起必限流，
  且返回的是**零结果页面而非报错**——不处理就会读成"没有竞争"。
  工具的应对是：识别 anomaly 页、**明确标为维度缺失**，
  并且**只尝试一次、不退避重试**（为一个不计分的维度等 36 秒是白等），
  同时把 SERP 刻意排除在评分之外，让裁决不随搜索引擎的心情波动。
- **两个数据质量陷阱**（已处理，但值得知道）：iTunes 的 `entity=software`
  **不排除游戏**（一个不存在的查询匹配到了 Fruit Ninja 的 37 万条评价）；
  Bing 自动补全会**静默剥掉**结尾的通用产品词（如 "software"），
  凭空制造出不存在的需求。
- 有频率限制，一次别跑太多词。

```

  global_scan.py               # 全球/英文引擎
  red_ocean_scan.py            # 中文市场引擎
  ladder_scan.py               # 收窄阶梯：宽词 → 窄口
  geo_scan.py                  # 地理套利：跨应用商店地区
  references/
    blue-ocean-methods.md      # 护城河（7 Powers）、ERRC 网格、六路径
    engine-global.md           # 全球引擎细节
    engine-cn.md               # 中文引擎细节
    modes.md                   # ladder + geo 细节
    calibration.md             # 全部实测校准锚点
    data-sources.md            # 数据源能力矩阵 + 静默失败陷阱

  validate_skill.py            # 规范校验 + token 预算 + 跑回归测试
  remeasure_cn.py              # 重测中文关键词、重新生成实测数据文档
                               #   （先探供给侧，被 IP 封锁就不生成半成品）
tests/
  test_decide.py               # 全球引擎裁决矩阵的离线回归
  test_cn_engine.py            # 中文引擎裁决分派与需求源的离线回归

  test_scope_guard.py          # 超范围（实体产品）拒绝作答

  trigger_eval.json            # 20 条触发评估 query
docs/
  实测数据-中文.md               # 18 个中文关键词的实测评分与反例分析
README.md / README.zh.md       # 英文版 / 中文版说明
```
